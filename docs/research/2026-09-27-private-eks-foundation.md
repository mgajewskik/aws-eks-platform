# Network, access, registry, and DNS for the private EKS foundation

- Date: 2026-09-27
- Status: preliminary architecture research; no AWS or DNS changes made
- Scope: one AWS account in Stockholm (`eu-north-1`), with `mgajewskik.dev` authoritative on Cloudflare

## Network findings

Regional NAT Gateway is available in commercial AWS Regions, including Stockholm. It is a VPC-level resource and needs no hosting public subnet. All three private subnets can route outbound traffic to the same NAT ID. AWS manages its route table with an internet-gateway route. Automatic expansion into a new AZ can take up to 60 minutes, with traffic crossing AZs in the meantime. This is documented service behavior, not measured recovery or availability for this platform. [AWS availability announcement](https://aws.amazon.com/about-aws/whats-new/2025/11/aws-nat-gateway-regional-availability/), [Regional NAT behavior](https://docs.aws.amazon.com/vpc/latest/userguide/nat-gateways-regional.html).

AWS bills regional NAT per active AZ-hour, plus data processing and applicable transfer and public IPv4 charges. Three active AZs mean three NAT-hours per elapsed hour. One resource therefore simplifies management without promising single-AZ pricing. No Stockholm cost estimate has been calculated, and the empty configuration's cached cost cannot price this design. [VPC pricing](https://aws.amazon.com/vpc/pricing/).

An internet-facing ALB requires public subnets in at least two AZs. Targets in an AZ that the ALB has not enabled do not receive traffic. Three public subnets are the candidate for serving workload targets across the proposed three AZs. Each ALB subnet needs at least a `/27` and eight free addresses. An NLB can use a single AZ, but that frontend does not meet a multi-AZ ingress objective. NAT carries outbound connections; it is not the path for unsolicited public ingress. [ALB subnet requirements](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/application-load-balancers.html), [NLB AZ behavior](https://docs.aws.amazon.com/elasticloadbalancing/latest/network/availability-zones.html), [NAT basics](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-nat-gateway.html).

The checkout pins Terraform 1.16.1 but has no selected AWS provider or implemented VPC module. The initial research considered an external VPC module; the owner subsequently rejected external and vendored prebuilt modules in [ADR-0005](../adr/0005-build-terraform-modules-from-resources.md). The design now uses repository-owned modules built from provider resource blocks. The AWS provider documents regional `aws_nat_gateway` with `availability_mode = "regional"` and `vpc_id`. Confirm an exact released provider version and route ownership before writing code; the upstream branch link is mutable. [Provider resource documentation](https://github.com/hashicorp/terraform-provider-aws/blob/main/website/docs/r/nat_gateway.html.markdown).

Future TGW integration requires non-overlapping VPC addresses, attachment coverage in each participating AZ, and routes in both directions. AWS recommends separate small attachment subnets, for example `/28`. Reserve address space now; creating attachments and routes can wait. The networking account retains ownership of TGW sharing, acceptance policy, and TGW route tables. Custom private-zone DNS needs a separate resolution design. [TGW attachment limits](https://docs.aws.amazon.com/vpc/latest/tgw/tgw-vpc-attachments.html), [TGW design guidance](https://docs.aws.amazon.com/vpc/latest/tgw/tgw-best-design-practices.html), [TGW sharing](https://docs.aws.amazon.com/vpc/latest/tgw/working-with-transit-gateways.html).

## Administrative access findings

A private-only EKS API requires a routed path from the VPC or a connected network, plus security-group permission to TCP 443 and identity authorization. Its public DNS name can resolve to private VPC addresses; resolving the name does not supply a network route. EKS private DNS requires VPC DNS support and hostnames enabled with AmazonProvidedDNS. [EKS endpoint access](https://docs.aws.amazon.com/eks/latest/userguide/cluster-endpoint.html).

SSM remote-host forwarding exposes a selected remote TCP port locally. It does not provide general laptop routing or private DNS. For the requested laptop access, a candidate is a private SSM-managed bastion with SSH over SSM and sshuttle scoped to the VPC CIDR, with `--dns`. This requires SSH authentication and sshd on the bastion, Python, and local elevated routing privileges. Common Linux sshuttle methods carry TCP and ordinary port-53 DNS, not arbitrary UDP. Validate the actual laptop resolver and tunnel before promising connectivity. No local integration probe has run. [SSM forwarding](https://docs.aws.amazon.com/systems-manager/latest/userguide/session-manager-working-with-sessions-start.html), [SSH over SSM](https://docs.aws.amazon.com/systems-manager/latest/userguide/session-manager-getting-started-enable-ssh-connections.html), [sshuttle usage](https://sshuttle.readthedocs.io/en/stable/usage.html), [sshuttle methods](https://sshuttle.readthedocs.io/en/stable/manpage.html).

The bastion needs outbound SSM connectivity through NAT or suitable VPC endpoints. SSM removes the need for an internet-facing SSH listener, but access still needs scoped IAM and security-group rules. SSM does not log SSH or port-forwarding payloads. An audited session start is not a command transcript. [SSM private connectivity](https://docs.aws.amazon.com/systems-manager/latest/userguide/setup-create-vpc.html), [session logging limits](https://docs.aws.amazon.com/systems-manager/latest/userguide/session-manager-logging.html).

"Only through the bastion" must distinguish human administration from workload traffic. The load balancer needs an allowed path to its private targets, and nodes need cluster communication. Define each path with source, destination, port, and identity constraints. The future TGW connection must not silently bypass the administrative boundary. This is a design recommendation, not evidence of implemented isolation.

sshuttle 1.3.2 documents both SSH configuration support and `--dns` forwarding to the remote resolver. Combining this with AWS's SSH-over-SSM ProxyCommand is an inference from those interfaces, not an integration verified here. For a bastion using AmazonProvidedDNS, associated private hosted-zone names can resolve on the remote side. Forward DNS maps names to addresses; reverse lookup needs a PTR record. Browser DNS-over-HTTPS can bypass port-53 interception. Scope the traffic proxy to the VPC rather than all destinations, and verify exclusions because sshuttle cannot automatically identify the SSH endpoint when ProxyCommand is used. [sshuttle usage](https://sshuttle.readthedocs.io/en/stable/usage.html), [sshuttle DNS options](https://sshuttle.readthedocs.io/en/stable/manpage.html), [VPC Resolver](https://docs.aws.amazon.com/vpc/latest/userguide/AmazonDNS-concepts.html).

Private operator applications have two candidate access paths. For the lowest initial cost, retain ClusterIP services and use laptop-side `kubectl port-forward` bound to localhost over the private API connection. For stable private hostnames, use an internal ALB and a VPC-associated private DNS zone. An internal ALB adds billable load-balancer capacity. Neither choice exposes the operator UI publicly. Kubernetes `cluster.local` names and ClusterIP addresses do not become laptop-accessible merely because sshuttle reaches the VPC. [Kubernetes port forwarding](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_port-forward/), [Kubernetes DNS](https://kubernetes.io/docs/concepts/services-networking/dns-pod-service/), [EKS ALB integration](https://docs.aws.amazon.com/eks/latest/userguide/alb-ingress.html).

Later acceptance must separately demonstrate laptop resolution of a known private-zone name, a permitted TCP connection, private EKS API authorization, and failure of operator UI access from an unconnected client. No live commands were run. The owner selected an internal load balancer with private DNS; the earlier ALB proposal is now reopened by the Istio requirement below. Port forwarding remains a diagnostic alternative.

## Registry findings

Amazon ECR pull-through cache supports Amazon ECR Public, `registry.k8s.io`, and public Quay without upstream credentials. Docker Hub, GitHub Container Registry, Azure Container Registry, GitLab Container Registry, and Chainguard require credentials in AWS Secrets Manager. GitLab support covers its SaaS registry. ECR-to-ECR cache is available with IAM access, including a future cross-account source. A private image needs a supported authenticated upstream and credentials with access to that image; the documented Quay rule has no authentication path. A registry outside the supported list has no ECR pull-through rule; copy its images to a normal private ECR repository if required. [ECR supported upstreams](https://docs.aws.amazon.com/AmazonECR/latest/userguide/pull-through-cache.html), [ECR migration options](https://docs.aws.amazon.com/AmazonECR/latest/userguide/migrate-from-third-party.html), [cross-account ECR cache](https://docs.aws.amazon.com/AmazonECR/latest/userguide/pull-through-cache-private.html).

The cache is explicit in the image URI, not a transparent mirror of arbitrary image references. For example, Docker Hub's `nginx` image uses `<account>.dkr.ecr.eu-north-1.amazonaws.com/docker-hub/library/nginx:<tag>`; the `library/` segment matters for Docker Hub official images. Helm values and GitOps manifests must point to the chosen ECR URI. Creating a missing repository needs `ecr:CreateRepository`; importing uncached images needs `ecr:BatchImportUpstreamImage`. Node IAM must also allow ECR image pulls. [Pull URI examples](https://docs.aws.amazon.com/AmazonECR/latest/userguide/pull-through-cache-working-pulling.html), [cache IAM permissions](https://docs.aws.amazon.com/AmazonECR/latest/userguide/pull-through-cache-iam.html), [ECR images on EKS](https://docs.aws.amazon.com/AmazonECR/latest/userguide/ECR_on_EKS.html).

ECR serves a cached tag without checking upstream if it validated that image within the past 24 hours. After that window, ECR checks for an update; if the check fails, it can serve the last cached image. Authenticated upstream checks use the configured upstream account, so the cache reduces repeat downloads but cannot promise freedom from that account's limits or make the first pull independent of upstream availability. Docker Hub still applies pull limits to eligible accounts. Prefer pinned digests where repeatability matters, and do not enable tag immutability on repositories that must refresh a tag. The upstream secret must have the `ecr-pullthroughcache/` name prefix and reside in the same account and Region as its rule. [ECR cache behavior and caveats](https://docs.aws.amazon.com/AmazonECR/latest/userguide/pull-through-cache.html), [Docker Hub pull limits](https://docs.docker.com/docker-hub/usage/pulls/).

For an ECR interface endpoint, AWS says the first pull through a cache rule needs a path to the internet through a NAT gateway; later pulls of that image do not. An ECR-only, no-egress design must prepopulate each image through another suitable path before nodes need it. EKS private-cluster guidance also calls for `ecr.api`, `ecr.dkr`, and S3 endpoints for private ECR pulls. [ECR VPC endpoint caveat](https://docs.aws.amazon.com/AmazonECR/latest/userguide/vpc-endpoints.html), [EKS private-cluster endpoints](https://docs.aws.amazon.com/eks/latest/userguide/private-clusters.html).

The literal rule "every platform image uses our own ECR cache" does not automatically cover EKS managed add-ons. AWS says these add-ons pull from AWS-owned ECR repositories replicated into each EKS Region, including Stockholm, according to the add-on installation mechanism. Their node pulls already use ECR and can use ECR VPC endpoints, but they do not use this account's cache URI. Treat AWS-managed add-ons as an explicit exception, or choose self-managed add-ons with supported image override and accept their upgrade ownership. Inspect each selected add-on and bootstrap image before promising full coverage. [EKS add-on registries](https://docs.aws.amazon.com/eks/latest/userguide/add-ons-images.html), [EKS add-on catalog](https://docs.aws.amazon.com/eks/latest/userguide/workloads-add-ons-available-eks.html).

## DNS findings

Cloudflare can remain authoritative for `mgajewskik.dev` while a Route 53 **public** hosted zone owns `eks.mgajewskik.dev`. Create the child zone first, then put its four assigned Route 53 name servers in `NS` records at `eks` in the Cloudflare parent. Records at and below `eks.mgajewskik.dev` then belong in the child zone. Do not leave a conflicting parent `A`, `AAAA`, or `CNAME` at the delegated name. Cloudflare's proxy, CDN, and security features do not apply to the delegated subdomain. If those features are required for a hostname, delegation is the wrong assumption and needs a separate design. [Route 53 delegation from another DNS provider](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/CreatingNewSubdomain.html), [Cloudflare outgoing delegation](https://developers.cloudflare.com/dns/manage-dns-records/how-to/subdomains-outside-cloudflare/), [Cloudflare NS conflict](https://developers.cloudflare.com/dns/manage-dns-records/troubleshooting/existing-ns-record/).

The initial ALB research considered ACM DNS validation. The owner subsequently required ACME automation; the proposed cert-manager DNS-01 flow below replaces that certificate approach. ACM validation CNAMEs and ACME challenge TXT records are different mechanisms. [ACM DNS validation](https://docs.aws.amazon.com/acm/latest/userguide/dns-validation.html).

The same delegation works for the selected `aws.mgajewskik.dev` namespace, intended for reuse beyond EKS. Neither label inherently provides better security. This is a design inference: authorization depends on zone and record permissions, while application access depends on network and identity controls. A broad reusable zone needs narrower permissions for any EKS DNS automation, limited to its intended record names, types, and actions. [Route 53 record permission conditions](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/resource-record-sets-permissions.html).

A separate private suffix such as `internal.aws.mgajewskik.dev` avoids shadowing public application names in `aws.mgajewskik.dev`. Private zones associate with VPCs; do not publicly delegate the private zone. An overlapping private zone returns NXDOMAIN for missing records rather than falling back to the corresponding public zone. A private name alone does not secure a public endpoint. [Private hosted zones](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/hosted-zones-private.html), [private-zone resolution rules](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/hosted-zone-private-considerations.html).

## Security controls and address scope

The owner requests security groups and custom NACLs while allowing NAT egress initially. SGs are stateful controls on resource network interfaces. NACLs are stateless subnet controls and require explicit return paths. AWS documents ALB and NAT ephemeral ports across `1024-65535`; restricting those without a traffic matrix can break valid connections. The candidate uses coarse public/private NACL boundaries and precise SG sources for ALB targets, the private API, and the internal ALB. It does not claim pod isolation from subnet filtering. [AWS NACL behavior](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-network-acls.html), [return ports](https://docs.aws.amazon.com/vpc/latest/userguide/custom-network-acl.html), [ALB security groups](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/load-balancer-update-security-groups.html).

EKS requires control-plane/node paths and workloads add DNS, webhooks, health probes, and image-pull traffic. EKS recreates its cluster SG self rules after updates if they were removed. This is separate from the unused VPC default SG, which the proposed baseline leaves without rules. AmazonProvidedDNS cannot be filtered with SGs or NACLs. VPC Flow Logs aid observation but are not packet capture, workload policy, or evidence that all traffic is secure. [EKS SG requirements](https://docs.aws.amazon.com/eks/latest/userguide/sec-group-reqs.html), [Amazon DNS limitations](https://docs.aws.amazon.com/vpc/latest/userguide/AmazonDNS-concepts.html), [VPC Flow Logs](https://docs.aws.amazon.com/vpc/latest/userguide/flow-logs.html).

CGNAT/shared address space `100.64.0.0/10` is distinct from RFC 1918 private space and is excluded by user requirement. It does not inherently lose packets; overlapping routes can send traffic to the wrong destination. A read-only route observation found local ranges outside the candidate `10.80.0.0/16` VPC and `10.81.0.0/16` service CIDR. Disconnected VPNs and future organizations still need overlap checks. The allocation table is in the plan. [RFC 6598](https://www.rfc-editor.org/info/rfc6598/), [AWS VPC CIDR rules](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-cidr-blocks.html).

### Initial ACME proposal and teardown limitation

The following cert-manager design was the initial proposal. The owner subsequently required certificate reuse across rebuilds; the retained-certificate comparison below reopens issuance ownership.

cert-manager with a Route 53 DNS-01 solver can issue certificates for private operator names by publishing challenge TXT records in the public `aws.mgajewskik.dev` zone. The application endpoints and A records can remain private. Scope the issuer's AWS identity to the required DNS operations and explicitly select the public hosted-zone ID. Its credentials can come from EKS Pod Identity or IRSA after those prerequisites exist. Keep certificate private keys in runtime TLS Secrets, outside Terraform values and Git. [DNS-01 challenges](https://letsencrypt.org/docs/challenge-types/), [Route 53 solver](https://cert-manager.io/docs/configuration/acme/dns01/route53/), [cert-manager Certificate lifecycle](https://cert-manager.io/docs/usage/certificate/).

The private `internal.aws` zone can shadow public challenge TXT records from the cluster's resolver. Selecting `hostedZoneID` controls where records are written, not the separate DNS self-check. Configure cert-manager's DNS-01 self-check with public recursive resolvers and recursive-only mode, then validate staging issuance. Leave laptop private DNS resolution on its VPC resolver path. Kubernetes Gateway API uses `certificateRefs`; the Istio `networking.istio.io` Gateway uses `credentialName`. Select the API and validate Secret namespace and gateway readiness rather than assuming issuance means serving works. [DNS-01 self-check controls](https://cert-manager.io/docs/configuration/acme/dns01/), [Gateway API TLS](https://gateway-api.sigs.k8s.io/guides/user-guides/tls/), [Istio cert-manager integration](https://istio.io/latest/docs/ops/integrations/certmanager/).

With disposable cluster state, teardown removes ACME account keys and issued certificate Secrets. A later deployment issues afresh rather than resuming ordinary renewal. Let's Encrypt production limits include five certificates for the same exact identifier set per seven days, so repeated rebuilds can exhaust issuance. Limits for a registered domain also span its subdomains. Prefer staging for development and a deliberate production issuer for browser-trusted demonstrations. Production certificates publish their names in certificate-transparency logs even when application DNS is private. Staging certificates are not trusted by ordinary browsers. Issuer mode and exact names versus wildcard scope remain open decisions. [Let's Encrypt limits](https://letsencrypt.org/docs/rate-limits/), [staging environment](https://letsencrypt.org/docs/staging-environment/), [certificate transparency disclosure](https://letsencrypt.org/docs/revoking/).

Use one ECR private registry in the Stockholm account, with separate pull-through prefixes for only the upstreams selected images actually need. Rewrite configured image references explicitly and preflight a representative first pull. The owner accepted AWS-managed EKS add-ons as an exception to the own-account cache objective. Keep future organization-wide ECR sharing as a later cross-account design. Shared public `aws.mgajewskik.dev` delegation and ECR persist; an internal NLB supplies private operator access. Terraform owns both foundational controllers and baseline Karpenter custom resources. Workload data is disposable. None of these capabilities is deployed.

Before the relevant implementation slices, settle the image inventory, upstream credentials, retention policy, and hostnames that will use ACME certificates. The AWS-managed add-on image exception and initial NAT egress are accepted. No live DNS records, registry settings, or cloud resources were inspected in this research.

### ExternalDNS ownership

ExternalDNS can reconcile Route 53 records from Kubernetes resources using scoped workload identity. Use the exact public/private hosted-zone IDs and separate identities, not unrestricted account-wide write access. Terraform owns zones and delegation; the certificate workflow owns validation records. [AWS integration](https://kubernetes-sigs.github.io/external-dns/latest/docs/tutorials/aws/).

The proposed two-instance setup filters public/private sources separately, restricts zone types, and excludes the private operator suffix from public publication. Use a TXT registry with stable, distinct ownership IDs and a chosen sync policy. Remove owned application records before tearing down controllers to avoid stale records. Owner IDs must not be shared by concurrent clusters. These are design recommendations requiring dry-run and later live verification. [Flags](https://kubernetes-sigs.github.io/external-dns/latest/docs/flags/), [TXT ownership](https://kubernetes-sigs.github.io/external-dns/latest/docs/registry/txt/).

Gateway API route sources support hostname requests and gateway targets; Ingress and Istio-native sources also exist. Select sources after choosing the Istio API. ExternalDNS creates DNS records, not certificates or domain registrations. No ExternalDNS version is pinned locally. Context7 did not resolve this project, so research used official upstream documentation directly. [Gateway API route sources](https://kubernetes-sigs.github.io/external-dns/latest/docs/sources/gateway-api/).

### Retained certificates and native AWS ACME

AWS now offers an ACM ACME endpoint, including Stockholm. An administrator prevalidates domains with persistent DNS CNAMEs and supplies external account binding credentials to an ACME client. This avoids per-order DNS-01 TXT changes. These certificates last 45 days; the client holds the private key and renews them. ACM managed renewal and certificate export do not apply to this ACME path, and these certificates cannot attach to AWS-integrated listeners. An ACM inventory ARN does not recover a lost client key. This corrects the earlier omission of native AWS ACME. [ACM ACME](https://docs.aws.amazon.com/acm/latest/userguide/acm-acme.html), [regional availability announcement](https://aws.amazon.com/about-aws/whats-new/2026/07/aws-certificate-manager-acme/).

Standard ACM certificates requested through the AWS API are a separate option. A retained exportable public certificate supports Envoy with ACM-managed renewal. External Secrets Operator documents an ACM provider that exports its PEM bundle into a Kubernetes TLS Secret and refreshes after renewal. Scope export access to the selected certificate ARN. Exact ESO version support must be verified before implementation. Automatic renewal eligibility requires use by an integrated service or export since issue/last renewal; a cluster absent across renewal cycles needs an off-cluster export strategy. Non-exportable ACM certificates cannot supply an Envoy private key. Their use on ALB/NLB TLS listeners would change the accepted termination boundary. [ACM exportable certificates](https://docs.aws.amazon.com/acm/latest/userguide/acm-exportable-certificates.html), [renewal eligibility](https://docs.aws.amazon.com/acm/latest/userguide/managed-renewal.html), [ESO ACM provider](https://external-secrets.io/latest/provider/aws-certificate-manager/).

Cloudflare Universal SSL is an edge service for proxied traffic, not a downloadable certificate/private-key bundle for the Istio gateway. Origin CA certificates secure the Cloudflare-to-origin hop and are not trusted by ordinary browsers accessing an internal NLB directly. Delegating a child zone to Route 53 does not put its traffic behind Cloudflare's proxy. These options therefore do not satisfy the same direct public/private ingress contract. Using a Cloudflare DNS plugin with an independent public ACME issuer is possible, but it remains DNS-01, and challenges for the delegated child belong to Route 53 unless challenge delegation is designed separately. [Universal SSL limitations](https://developers.cloudflare.com/ssl/edge-certificates/universal-ssl/limitations/), [Origin CA](https://developers.cloudflare.com/ssl/origin-configuration/origin-ca/).

The lower-cost recommendation is an ACME client outside disposable EKS with retained account, renewal configuration, certificate, and key state. Certbot's Route 53 plugin automates DNS-01. A successful-renewal deploy hook can publish the full chain and matching key to a retained Secrets Manager secret; ESO then reads it into each replacement cluster. This proposed composition needs implementation validation. An owner-machine timer only runs while that machine is available, so require renewal and validity checks before deployment. Unattended renewal while both EKS and the laptop are absent needs a retained runner. No cert-manager is required inside EKS for this path. [Certbot renewal and hooks](https://eff-certbot.readthedocs.io/en/stable/using.html), [Route 53 plugin](https://certbot-dns-route53.readthedocs.io/en/stable/), [ESO Secrets Manager provider](https://external-secrets.io/latest/provider/aws-secrets-manager/).

Issue only when needed, not at every deployment. Existing certificates work when their names, chain, key, validity, and trust match the gateway. They still need renewal before expiry. Separate wildcard certificates for `*.aws.mgajewskik.dev` and `*.internal.aws.mgajewskik.dev` are an optional way to support changing application labels with fewer issuance events; the first wildcard does not cover the second namespace or the zone apex. Broader key scope is the tradeoff. Key material stays outside Terraform state and Git. Repeated re-issuance limits remain relevant if retained state is lost. [Let's Encrypt challenge types](https://letsencrypt.org/docs/challenge-types/), [rate limits](https://letsencrypt.org/docs/rate-limits/).

Certificate alternatives are proposals, not accepted ownership changes. Current pricing and the ALB/NLB comparison belong in [the cost document](../cost.md), separate from the empty-configuration cache.

### Accepted retention and Lambda renewal

The owner subsequently accepted the cheaper retained Let's Encrypt option with Secrets Manager and ESO delivery. This supersedes the open issuer comparison above without selecting paid ACM or Cloudflare certificates. [ADR-0008](../adr/0008-retain-acme-certificates-outside-eks.md) records the accepted lifecycle. Q17 accepts one wildcard, flat application names, split-view DNS, and a scheduled Lambda runner. The owner closed the architecture interview and assigned implementation to separate staged plans; earlier alternatives above are research history, not selected designs.

An EventBridge schedule can invoke a retained renewal Lambda. A Lambda without VPC attachment has internet access independently of the disposable EKS VPC and NAT. It can therefore perform public DNS-01 while the cluster is absent. Its maximum execution is 900 seconds, so bounded CA/DNS waits and a failure path are required. [Scheduled invocation](https://docs.aws.amazon.com/lambda/latest/dg/with-eventbridge-scheduler.html), [internet access](https://docs.aws.amazon.com/lambda/latest/dg/configuration-vpc-internet.html), [Lambda limits](https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html).

Lambda `/tmp` is not durable issuer storage. Secrets Manager limits one value to 65,536 bytes; a multi-file ACME client state archive may require a retained encrypted/versioned S3 object instead. Choose the client and measure its state before selecting the format. The published gateway certificate/key bundle remains in Secrets Manager. [Execution environment](https://docs.aws.amazon.com/lambda/latest/dg/lambda-runtime-environment.html), [Secrets Manager limits](https://docs.aws.amazon.com/secretsmanager/latest/userguide/reference_limits.html).

The design must check whether renewal is due, prevent concurrent writers, and handle duplicate asynchronous delivery. Retain a successful renewal before publishing, verify the matching key/chain, and preserve the last valid published bundle on failure. Retry publishing if renewal succeeded but secret delivery failed, even when the next renewal check is a no-op. Add failure and expiry monitoring. These are design inferences from documented component behavior, not a tested Lambda integration. [Lambda asynchronous invocation](https://docs.aws.amazon.com/lambda/latest/api/API_Invoke.html), [Certbot renewal](https://eff-certbot.readthedocs.io/en/stable/using.html).

One wildcard covers one label: `*.aws.mgajewskik.dev` covers `argocd.aws.mgajewskik.dev`, not the apex or `argocd.internal.aws.mgajewskik.dev`. The accepted flat naming uses public/private zones both called `aws.mgajewskik.dev`. Because Route 53 does not fall back to public DNS for a missing matching private record, private ExternalDNS must also reconcile public app records needed inside the VPC. Public ExternalDNS selects only public resources; private operator addresses never enter the public zone. Wildcard certificate scope does not imply a wildcard DNS record or endpoint visibility. [Wildcard definition](https://letsencrypt.org/docs/glossary/), [Route 53 split-view DNS](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/hosted-zone-private-considerations.html).
