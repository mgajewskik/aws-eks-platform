# Testing the EKS platform without test-managed cluster lifecycle

- Date: 2026-09-27
- Status: research and proposed test boundaries; not an implementation or deployment result
- Scope: Terraform, GitOps, policies, and an existing manually deployed EKS cluster

## Recommendation

Keep required checks independent of cloud credentials and free of cloud mutations. Use pytest as the only test runner, with Python dependencies recorded in [`pyproject.toml`](../../pyproject.toml) and [`uv.lock`](../../uv.lock). For Terraform, run formatting, validation, linting, and scanning now. Add pytest assertions over safe local artifacts only when real modules give those assertions value. Validate rendered GitOps manifests and policy examples through pytest once those components exist. Run read-only AWS and Kubernetes pytest cases as a separate, opt-in suite against the owner's existing deployment. Run tests that create temporary workloads only when the owner explicitly selects the scenario and its cleanup procedure.

The test suite must never provision or destroy EKS, its VPC, or the Terraform-managed platform. This follows the repository's [local deployment decision](../adr/0003-ci-checks-apply-is-local.md). GitOps owns desired Kubernetes objects, while controllers can create subordinate AWS resources such as ALBs and EBS volumes. The [AWS Load Balancer Controller](https://kubernetes-sigs.github.io/aws-load-balancer-controller/latest/deploy/scaling/) can change AWS resources to match Kubernetes objects; the [EBS CSI driver](https://docs.aws.amazon.com/eks/latest/userguide/ebs-csi.html) manages volumes for Kubernetes storage.

In this checkout, `platform/main.tf` is empty, and `gitops/` has no manifests. No deployed cluster, GitOps engine, policy engine, or working live test is established by this research. [`scripts/checks.sh`](../../scripts/checks.sh) runs the local pytest harness, Terraform format, conditional validation and linting, and Trivy. The pytest configuration selects `tests/harness` by default. These checks need no AWS credentials and make no cloud mutations. Mise nevertheless loads the owner's `.env.local` for every local task, so its variables are inherited and must not be printed. Checks are not guaranteed offline: `terraform init` can fetch providers or modules, and Trivy can refresh its checks bundle. [Terraform init](https://developer.hashicorp.com/terraform/cli/commands/init), [Trivy built-in checks](https://trivy.dev/docs/latest/scanner/misconfiguration/check/builtin/).

## Compare the test tools

| Tool | Useful evidence | Limit and decision |
|---|---|---|
| Native Terraform tests with `mock_provider` | Input validation, conditional resources, module outputs, and planned relationships under the provider schema. [HashiCorp mocking guide](https://developer.hashicorp.com/terraform/language/tests/mocking). | Researched, not adopted. `.tftest.hcl` runs would create a second test suite outside pytest. HashiCorp says a run defaults to `apply`; with real providers it can create billed resources, then attempt cleanup. Even a plan-only mocked run needs every reachable provider mocked and cannot prove AWS accepts the plan. [Test language](https://developer.hashicorp.com/terraform/language/tests), [test command](https://developer.hashicorp.com/terraform/cli/commands/test). |
| Terratest against existing resources | Go assertions can inspect AWS APIs through its [AWS helpers](https://terratest.gruntwork.io/docs/getting-started/packages-overview/). | Researched, not adopted. Terratest's documented Terraform flow runs apply and destroy, which must never point at this platform for testing. A read-only Go suite is possible, but would add another test runner and language. [Quick start](https://terratest.gruntwork.io/docs/getting-started/quick-start/), [testing environment guidance](https://terratest.gruntwork.io/docs/testing-best-practices/testing-environment/). |
| `pytest`, `boto3`, and the Kubernetes Python client | Pytest is the chosen runner for local harness checks now and future platform assertions. Pytest markers can separate live tests; the official Kubernetes client reads kubeconfig and supports API GET and LIST operations. [Pytest markers](https://docs.pytest.org/en/stable/how-to/mark.html), [Kubernetes Python client](https://github.com/kubernetes-client/python). | Add `boto3` and the Kubernetes client through uv only after a manually deployed platform supplies useful live assertions. Keep live paths outside default `tests/harness`, required checks, and CI. |
| Kubernetes manifest and policy checks | Pytest can invoke a renderer and validator, then assert their exit status and expected policy decisions. [Kustomize renderer](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_kustomize/), [Kubeconform](https://github.com/yannh/kubeconform). Kyverno and Gatekeeper also offer native test commands, but those would be separate suites if invoked on their own. [Kyverno test](https://kyverno.io/docs/kyverno-cli/reference/kyverno_test/), [Gatekeeper gator](https://open-policy-agent.github.io/gatekeeper/website/docs/gator/). | Add pytest cases with the first GitOps manifests and selected policy engine. Pin validation to the target Kubernetes version and supply custom-resource schemas. Do not silently ignore missing schemas. Schema checks cannot reproduce admission or controller reconciliation. |

This is the smallest coherent stack for the planned system: pytest and static checks now; pytest-driven manifest and policy checks when GitOps exists; opt-in pytest live assertions only after manual deployment. For Terraform, format, validate, lint, and scan can reject many local defects. Pytest can inspect safe artifacts at implemented module seams, but it cannot establish the planned AWS resource graph without a trustworthy plan or Terraform's separate mock test language. Do not turn a credentialed `terraform plan` into a required check to close that gap. The repo pins Terraform 1.16.1 through mise, so invoke the pinned runtime rather than relying on a bare executable found earlier on `PATH`.

## What each layer can establish

| Layer | First useful scenarios | What a pass does not establish |
|---|---|---|
| Required local checks | Pytest harness cases, Terraform formatting and validation, TFLint, Trivy, then pytest-driven safe artifact and rendered-manifest checks when files exist. | A planned AWS resource graph, successful deployment, healthy controller, or working data path. |
| Opt-in read-only live suite | Expected EKS account, region, ARN, endpoint, and status; VPC and subnet identity; nodes and add-on readiness; GitOps reconciliation; selected workload status. | Dynamic ALB or EBS creation when no test workload exists, policy enforcement on real creates, or full network connectivity. |
| Explicitly user-run workload scenarios | A small application; expected policy admission results; Ingress through ALB; PVC through EBS; optional TGW traffic path. | Cleanup, until both Kubernetes objects and their AWS resources are independently checked as gone. |

For the read-only suite, require explicit expected account, `eu-north-1` region, cluster ARN or name, and kubeconfig context. Call STS to establish the actual AWS account, describe the exact EKS cluster, and compare its API endpoint with the selected kubeconfig target before cluster assertions. Stop on any mismatch or missing value. Use AWS describe and list permissions and Kubernetes get and list permissions. Do not print credentials, Secrets, kubeconfig contents, or whole API responses. [STS identity](https://docs.aws.amazon.com/cli/latest/reference/sts/get-caller-identity.html), [EKS description](https://docs.aws.amazon.com/cli/latest/reference/eks/describe-cluster.html), [Kubernetes client](https://github.com/kubernetes-client/python).

A private-only EKS API requires the laptop or test runner to reach the VPC or a connected network. AWS credentials alone do not establish that path. [EKS endpoint access](https://docs.aws.amazon.com/eks/latest/userguide/cluster-endpoint.html). If the optional TGW attachment to a network account is enabled, inspect the attachment state, platform VPC routes, and the network account's TGW and return routes before claiming routing is configured. Attachment existence cannot prove end-to-end traffic. [Attachment description](https://docs.aws.amazon.com/cli/latest/reference/ec2/describe-transit-gateway-vpc-attachments.html), [VPC routes](https://docs.aws.amazon.com/cli/latest/reference/ec2/describe-route-tables.html), [TGW routing](https://docs.aws.amazon.com/vpc/latest/tgw/tgw-transit-gateways.html). Proving traffic requires a separate user-run scenario from the intended network endpoint.

Kubernetes server-side dry run can exercise API validation and admission without persisting an object. It requires the same create or update authorization as a real request, so keep it outside a strictly get/list suite if that permission matters. It cannot show whether an ALB, EBS volume, or Pod works after creation. [Kubernetes dry-run semantics](https://kubernetes.io/docs/reference/using-api/api-concepts).

## Bound mutating scenarios and costs

The owner has selected Stockholm (`eu-north-1`), a USD 100 monthly ceiling, availability across zones while the platform is deployed, and regular platform teardown. The research does not establish that this design fits the ceiling. [AWS EKS pricing](https://aws.amazon.com/eks/pricing/) charges for cluster time and separately for worker and storage resources; the run duration and retained resources matter as much as the intended high-availability topology. Keep the existing opt-in `mise run cost` task separate from checks and CI. Do not consume an Infracost run until billable topology and expected active hours can support a useful estimate. A cached estimate is evidence for a stated configuration and usage assumption, not an AWS spending cap.

Creating an Ingress can provision an ALB, and a PVC can provision an EBS volume. Both can outlive the test if reconciliation or cleanup fails. [EKS ALB guide](https://docs.aws.amazon.com/eks/latest/userguide/alb-ingress.html), [EKS EBS guide](https://docs.aws.amazon.com/eks/latest/userguide/ebs-csi.html). Before a user-run scenario, specify its expected account and cluster, unique resource names, namespace, maximum size and duration, expected cost, and cleanup inventory. Record the ALB and volume IDs the scenario actually creates. Delete the test Ingress before its IngressClass and verify the related AWS resources disappear. [Controller cleanup order](https://kubernetes-sigs.github.io/aws-load-balancer-controller/latest/guide/ingress/ingress_class/). Delete workload references and PVCs, then check the PV reclaim policy and AWS volume outcome before considering cleanup complete. A `Retain` policy leaves the backing asset for manual reclamation. [Kubernetes PV reclaim policies](https://kubernetes.io/docs/concepts/storage/persistent-volumes/).

Never use `terraform destroy` or a broad account cleanup as a test teardown. The owner may separately destroy the platform as a deliberate deployment operation. Workload tests are user-run, and cleanup must target only their recorded resources. If the controller leaves an AWS resource behind, report the exact resource and stop rather than removing unrelated resources.

## Open decisions

- The GitOps renderer, policy engine, Kubernetes version, custom-resource schemas, and controller versions are not selected here. Choose test fixtures after those implementations land.
- The EKS endpoint access mode and TGW ownership determine where live tests can run and which account can inspect routes.
- Billable topology, active hours per month, and teardown retention determine whether the USD 100 ceiling is realistic. The separate cost assessment must price those assumptions.

No offline or read-only test pass is a production-readiness guarantee. Full deployment, dynamic AWS reconciliation, and cleanup require evidence from a manually deployed environment and the bounded user-run scenarios above.
